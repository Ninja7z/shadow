## Product vision and non-negotiable decisions

1. Make the terminal experience excellent first. The user wants an installer inspired by Hermes/OpenCode: a single `npm`/`npx` entry point that detects missing prerequisites, installs managed dependencies, guides configuration one step at a time, and ends with useful commands.
2. The terminal-first product must be robust before the web interface exists.
3. Web interface / phase 5 is intentionally deferred to the `1.0.0` milestone. It should be optional and local-only initially, started by `web-shadow`, opening a localhost URL that users can click or copy into a browser. Terminal remains fully supported.
4. After `1.0.0`, prioritize maintenance and incremental evolution: bug/security fixes, reliability, performance, compatibility, provider/client integrations, and UX improvements. Do not rush major features at the cost of stability.
5. User's growth target: 1,000 GitHub stars within five months, with the clock starting on the actual public release date of `0.2.0`. Do not start the clock from this handoff date or promise the target as guaranteed.
6. User authorizes autonomous project work and GitHub commits/pushes in this project. User explicitly said they may be unavailable to approve npm publication. NEVER publish to npm without the user's explicit approval in that moment. Keep npm `latest` unchanged until approved.
7. User prefers direct, practical execution and progress anchored to the project goal. Avoid giant one-liners and unnecessary theory. Validate actual behavior and report only confirmed results.
