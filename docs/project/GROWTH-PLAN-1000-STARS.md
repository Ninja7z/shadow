# Shadow: 1,000 GitHub stars in five months

**Goal:** reach 1,000 GitHub stars during the five months beginning on the public release date of `shadow-gateway@0.2.0`.

**Baseline snapshot (2026-11-26):** GitHub API reported 1 star for `Ninja7z/shadow`. Recheck on 0.2.0 launch day and record the exact publication timestamp. The five-month deadline is calculated from that timestamp, not from the date of this planning document.

This is an ambitious target, not a guarantee. Stars must follow real product value and community trust.

## Before the clock starts

- Make 0.2.0 genuinely installable and useful from a clean Linux machine; validate Windows and macOS rather than advertising untested compatibility.
- Publish a bilingual README that immediately explains the problem, value, install command, supported providers/clients, security boundaries, and troubleshooting.
- Record reproducible install and smoke-test evidence. Clearly label tested vs experimental platforms.
- Add contribution guide, issue templates, security reporting instructions, roadmap and changelog.
- Prepare a short terminal demo showing first install through a successful request. Avoid polished marketing claims that exceed verified functionality.
- Establish baseline analytics that respect privacy: GitHub stars/forks/issues, npm downloads, referrers where available, contributors, and support/installation outcomes.

## Five-month operating plan

### Month 1 — Credibility and first users

- Announce 0.2.0 with a clear problem/solution story and a real demo.
- Share in relevant developer communities only where self-promotion is allowed; tailor each post to the community and contribute beyond the announcement.
- Publish a technical article on the terminal-first setup and safe dependency management.
- Personally support early adopters, turn repeated friction into fixes/docs, and close the loop on every useful issue.
- Measure install-to-success conversion, not just clicks.

### Month 2 — Proof and discoverability

- Publish real use cases for Claude Code, OpenCode, Cline, Aider, Continue and supported providers only after each is verified.
- Improve search discoverability: descriptive docs, comparison pages that are fair and factual, troubleshooting pages, and clear examples.
- Ask early users for honest feedback and optional testimonials; obtain permission before quoting them.
- Fix onboarding drop-off and platform-specific defects before adding breadth.

### Month 3 — Community and contributions

- Make first contributions easy with good-first-issue tasks, development setup, architecture notes and clear review expectations.
- Publish one useful technical update or demo regularly, not low-value daily promotion.
- Engage with adjacent open-source projects through integrations and genuine collaboration; do not mass-tag maintainers.
- Recognize contributors and publish transparent release notes.

### Month 4 — Integration-led growth

- Prioritize integrations requested by real users and compatible with the reliability roadmap.
- Publish practical walkthroughs and examples that demonstrate repeatable outcomes.
- Revisit the channels that generated successful installs and contributors; stop spending effort on high-traffic/low-conversion channels.
- Keep response times and issue closure healthy as usage grows.

### Month 5 — Retention and milestone

- Focus on reliability, upgrade experience, documentation freshness and user retention.
- Publish a transparent five-month community update with shipped work, metrics, lessons and next steps.
- Thank contributors and users; invite feedback without pressure.
- Report the final star count and other metrics honestly, whether or not the target was reached.

## Weekly scorecard

Record once per week:

| Metric | Why it matters |
|---|---|
| Stars and net new stars | Progress toward the goal |
| npm weekly downloads | Package discovery and usage proxy, not unique users |
| README views/referrers | Discovery sources |
| Install success reports | Actual product activation |
| Issues opened vs resolved | Support load and responsiveness |
| Contributors and merged PRs | Community health |
| Platform-specific failures | Compatibility quality |
| Repeat users / upgrade success | Retention and trust |

## Ethical growth rules

- No bought stars, bots, fake accounts, engagement pods, spam or misleading comparisons.
- Never inflate downloads, users, compatibility claims or test results.
- Ask for a star once at a natural success moment; never gate features or repeatedly nag.
- Protect user privacy in telemetry and diagnostics; redact tokens and configuration secrets.
- Prioritize product quality over a weekly star quota. The target is a compass, not permission to cut corners.
